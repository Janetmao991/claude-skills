# 独立审片（最多两轮）

全片渲染后、给 Janet 看之前，跑"独立审片 → 修改"，**最多两轮，两轮后无论还剩什么问题都先交给 Janet 看**（Janet 2026-11-17：不要自己无止境地跑审片；她说只跑一轮时就只跑一轮）。目的是让 Janet 拿到的版本已经过一遍挑错，她的时间花在判断方向上，而不是抓卡帧和错字。

做片的 agent 看自己的作品容易替它找理由，所以审片交给全新的子 agent。每轮同时派三个，分工不重叠：

| 审片人 | 看什么 | 拿到的材料 |
|---|---|---|
| A 综合审片 | 事实、贴题、文字和翻译、画面有没有出错、技术故障 | 全部：脚本、帧拼图、research、审片标准 |
| B 新观众 | 只看逻辑是否连贯，不了解这家公司的人能否一路跟上 | **只有** `narration.md`，不给脚本、research、框架和画面 |
| C 风格审片 | 只看画面好不好看、像不像这家公司 | 镜头拼图、手机尺寸拼图、参考帧 `ref-*.jpg`、`timeline.md`、`brand.ts`、`style-review.md`；不给 research |

为什么要把 B 分出来：A 为了核对事实要读 research，读完就"懂这家公司"了，会在脑子里自动补上视频没讲的那一步，看不出跳跃。B 只知道观众知道的东西，哪里接不上一读就卡住。

为什么要把 C 分出来（2026-11-16 加）：A 查的是画面"有没有出错"（跑题、遮挡、没标示意），不评"好不好看"。C 只管审美，标准见 `style-review.md`。

## 收敛规则（2026-11-16，Gamma 那期定的）

Gamma 那期第一轮三人一共提了五十多条，几乎全改了；第二轮换的新审片员又从零挑出一批新的，"必须改"反而更多。审片员越多、越独立，意见越多，照单全收会一直改下去。所以：

1. **每条意见先分级，按级处理：**

   | 级别 | 是什么 | 怎么处理 |
   |---|---|---|
   | 必须改 | 事实错误或说过头、明显故障、触发硬规则（`style-review.md` 第一部分）、B 的"看不懂" | 核实后一定改 |
   | 建议改 | 能更好，但不改也不算错 | **每位审片员最多挑最重要的三条改**，其余记进 fixes.md，不动 |
   | 请 Janet 判断 | 取决于口味，或者要删改内容结构（删一段、改问题范围） | **不自己改**，写进交付说明 |

2. **第二轮是验收，不是重审。** 仍然派三个全新的子 agent（保持独立），但任务书末尾加上"第二轮附加段"（见下），把第一轮的问题清单（只给问题，不给制作方的解释）交给它们逐条验收：修好了 / 没修好 / 改出了新问题。新发现只记"必须改"级别。
3. **停止条件：最多两轮，然后一定先交给 Janet。** 第二轮验收后不管还剩不剩"必须改"，都交片，剩下的写进交付说明由她决定，绝不开第三轮。不追求分数。Janet 说"跑一轮就行"时，第一轮改完就交，不跑第二轮。
   - "一轮"指 A、B、C 三个审片员同时审一次，不是一个审片员算一轮。
   - 修改后的重渲染只用来修帧差、黑帧这类技术检查，不再派审片员。
4. **画面问题先看能不能一次解决。** 如果几条意见指向同一个根源（比如"浅色截图和深色示意来回闪""出处标签压字""示意图太多"都源于没有统一的视觉主线），先回到 `visual-method.md` 的"视觉主线"一步改整体版式，而不是一条条打补丁。

## 流程

每一轮：

1. 生成审片材料（`--ref` 给参考视频：Janet 指定的参考片、公司官方发布片，生成参考帧给 C）：

   ```bash
   python3 tools/review_pack.py renders/<当前版本>.mp4 review/round-<N> --ref sources/broll/<官方片>.mp4 [--ref <参考片>.mp4]
   ```

2. 在同一条消息里启动 A、B、C 三个全新的子 agent（Agent 工具，`general-purpose`，不要 fork，不要 SendMessage 给上一轮的审片人），分别发任务书 A、B 和 `style-review.md` 里的任务书 C。**不要告诉它们你认为哪里好、改过什么。** 第二轮按收敛规则第 2 条加附加段。给 B 的任务书里不要提公司背景，也不要附其他文件路径。
3. 子 agent 经常被拦着不让写文件（2026-11-16 多次遇到），这时它会把内容放在回复里，原样存成对应的 findings 文件再往下走。拿到 `findings.md`（A）、`findings-flow.md`（B）和 `findings-style.md`（C）后，自己逐条核实：去看对应的帧、台词和出处。审片人也会看错，不要照单全收。B 说"看不懂"的地方，默认是真问题：它就是观众。
4. 按收敛规则分级处理，把结果写进 `review/round-<N>/fixes.md`：每条写"已改 / 不改（原因）/ 留给 Janet"。改逻辑时优先补上缺的那一步（一句交代、一个过渡），而不是把句子写得更长。
5. 重新配音（台词改了的话）、跑 `check_plan.py`、用新的输出名重新渲染，再进入下一轮。

## 第二轮附加段

第二轮给 A、B、C 的任务书末尾都加上这一段（把尖括号替换掉；给 B 的版本只附 B 自己那份第一轮清单）：

```
这是第二轮。上一轮的审片人提过下面这些问题（只有问题，没有制作方的解释）：<第一轮对应 findings 文件的路径>

先逐条验收，写在结果文件最前面：
| 第一轮的问题 | 修好了 / 没修好 / 改出了新问题 | 依据 |

然后再按原来的要求审，但新发现只记"必须改"级别（建议改最多三条，挑最重要的）。不要为了显得有用而挑新毛病。
```

## 交付给 Janet 时附上

几句话说明：两轮一共发现和修了什么（最重要的几条）、哪些没有改以及原因、哪些需要她拍板。附上 C 的硬规则检查结果和"和参考的差距"，分数只当粗略参考（同一版片子审两次，分数也会差零点几）。还要说明 reviewer 听不到声音，配音语气和节奏仍要她听。

## 任务书 A：综合审片

把尖括号替换后整段发给子 agent：

```
你是这条视频的独立审片人，和制作团队没有关系。你的任务是找出问题，不是肯定这条视频。

本期要回答的问题：<一句话问题>

材料（图片用 Read 可以直接看）：
- 成片：<video 绝对路径>/renders/<版本>.mp4（Read 打不开视频。需要看某一刻的帧时，用 ffmpeg -ss <秒> -i <成片> -frames:v 1 <输出.jpg> 抽出来再看）
- 脚本：<video 绝对路径>/SCRIPT.md
- 审片包：<video 绝对路径>/review/round-<N>/
  - timeline.md：每句台词的时间、中英文、画面类型
  - sheet-*.jpg：每 2 秒一帧的拼图，每格左上角是时间
  - cuts-*.jpg：每个切点前后的帧，每格左上角标 before / after 和切点时间
  - tech.md：时长、音量、静止段、配音听写报告
- 事实依据：<项目绝对路径>/research/ 和 <项目绝对路径>/<公司> — Framework.md
- 审片标准：~/.claude/skills/company-strategy-video/references/script-standards.md 和 visual-method.md

你看不到动态、也听不到声音，只能从帧、台词和报告判断。判断不了的写"无法判断"，不要猜。

按这个顺序审：

1. 事实：抽查脚本里的数字、人物说法和因果判断，能否在 research/ 找到依据？有没有把事后总结说成当时的策略，或说过头？列出查了哪些。
2. 贴题：哪些内容和本期问题没有直接关系，可以删？哪个点只说了做法，没说和策略的关系或结果？
3. 逻辑：因果判断是否成立、结论是否被证据支撑？（句子之间是否连贯、新观众能否跟上，另有专人审，你不用逐句查。）
4. 听感文字：哪里口语化、绕口、翻译不准？总结和结尾是否具体？原声的中英文是否对应？
5. 画面：哪里像 PPT？哪个画面和台词无关？同一素材是否反复或连用太久？素材里是否混入主持人、其他公司或失效页面？文字是否重叠、换行错位、被遮挡？有没有画面中间的大字或第二条字幕？重建和生成的画面是否标了"示意"？
6. 技术：切点前后是否有卡住、闪帧、黑帧？静止段里哪些是真问题？音量是否正常？

把结果写到 <video 绝对路径>/review/round-<N>/findings.md，每条一行：
（如果写文件被拦，就把完整内容原样放在你的最终回复里，由制作方存档。）

| 严重度 | 时间 | 类别 | 问题 | 依据 | 建议 |

严重度：必须改（事实错误、明显故障、跑题）/ 建议改 / 请 Janet 判断（取决于品味）。按严重度排序，最多 25 条，宁缺毋滥，不要为了凑数挑小毛病。

文件最后写两三句总体判断：这条视频最大的问题是什么。
```

## 任务书 B：新观众

把尖括号替换后整段发给子 agent。**只附 narration.md 一个文件。**

```
你是一位普通观众，第一次看这条视频。你没听说过视频里的公司和人物，也不了解这个行业的术语，但愿意认真看完。你只能看一遍，不能倒回去。

这条视频的全部旁白和原声字幕在：<video 绝对路径>/review/round-<N>/narration.md
（【播客原声】是受访者本人说的话的中文翻译。）

只读这一个文件，不要读同一文件夹或项目里的其他文件，不要上网查这家公司。你知道的，只能是视频已经告诉你的。

做法：

1. 从头往下读，读到每一句时，只用前面已经讲过的内容去理解它，不要往后看。
2. 遇到下面这些情况就停下来记一条：
   - 出现一个人名、公司名、术语或缩写，前面没交代它是什么
   - 这句话和上一句之间缺了一步：为什么突然讲这个？"所以""因此"前后其实推不出来
   - "他""这个""这种做法"指的是什么不清楚
   - 说了一个做法，但没说为什么这么做，或者没说结果
   - 一个数字或结果出现了，但不知道它说明了什么
   - 原声和前后旁白接不上：引用它是想证明什么？
   - 同一件事在不同地方用了不同的叫法，让人以为是两件事
   - 话题转到下一部分时没有过渡，你一时不知道现在在讲第几点
3. 每一条写：你卡在哪、你当时以为是什么意思、缺了哪句话就能跟上。只记真的让你卡住的地方，读得顺的不用夸。

读完后，合上文件（不要再看），凭记忆回答：
- 这条视频想回答什么问题？
- 它给出的答案是什么？分别是哪几点，每点为什么有效？
- 哪一点你最没听懂？

把结果写到 <video 绝对路径>/review/round-<N>/findings-flow.md：
（如果写文件被拦，就把完整内容原样放在你的最终回复里，由制作方存档。）

先写上面三个问题的回答，然后是问题表，每条一行，按播放顺序：

| 严重度 | 时间 | 卡在哪 | 我当时的理解 | 缺了什么 |

严重度：看不懂（不补就跟不上后面的内容）/ 有点跳（能猜到，但要停一下）。最多 20 条。
```

B 的复述是很好的检验：它复述出来的几点和脚本想讲的对不上，说明结构本身有问题，不是改几句话能解决的，要回头调整这一部分的顺序或铺垫。
